## Payment integrity boundary and unresolved decisions

**LEGACY-PAY-01 is PARTIALLY fixed, not resolved.** Six unsuppressed failures remain: amount and currency in PaymentInvariantTest, PaymentDefectVerificationTest and PaymentPersistenceIntegrationTest. The real SQL cases still demonstrate payment-state writes/conversion/notification for a signed/fetched paid response with incorrect monetary values. No claim of complete invalid-payment fulfillment protection is justified.

The application stores normalized link-creation amount/currency in mutable payment_response JSON and later overwrites that JSON during callbacks. Invoices can be edited. The owner must decide whether the original link amount/currency or current invoice amount/currency is authoritative, and what happens for missing/overwritten metadata, replaced links and edited invoices. An asynchronous clarification was requested; no answer has been received. No monetary baseline was invented. Once approved, compare exact minor units/currency before any write or fulfillment and retain all six negative invariants. Partial payments, FX, refunds, manual settlements and reversals need separate accepted rules; their behavior was not redesigned.

Stored identity metadata is required for this callback path: missing/malformed/nonmatching stored metadata now fails closed to the existing signin redirect. Legacy invoices lacking it need reviewed reconciliation/reissue, not an unsafe fallback. Fetched resource id/reference must be present and match the signature. Existing SDK HMAC verification and redirect response remain unchanged. This handler is a GET browser callback; webhook duplicate/out-of-order semantics do not by themselves prove this freshly fetched resource can regress.

Completed state is the existing exact payment_status value `Transction Success`, rather than status=1 alone (which also represents approval). Other legacy completion strings/manual settlements need owner classification. A recorded success with incomplete conversion may retry conversion on a later paid callback; nonpaid callbacks cannot erase the success. No new payment ledger/table/unique constraint was added; duplicate invoice_name data and multiple payment attempts remain acceptance/design gates.

## Concurrency and cross-store recovery

The transaction holds the invoice row lock through existing Common finalization. Two successful callbacks therefore serialize and recheck conversion under the same lock. The provider GET occurs before acquiring the lock. Common may perform rendering, cloud/provider operations and mail during conversion, so lock duration is longer; no implicit deadlock retry was added because repeating external effects would be unsafe.

`tests/run-concurrent.php` verifies the exact owned MySQL data directory and initially empty disposable schema; workers additionally verify both runtime identities through run-real.php. It invokes two restricted PHP workers with real Laravel routing, MySQL, Common, Dompdf and in-memory Swift/cloud/provider boundaries. The supervisor holds the invoice lock until both child connection IDs appear simultaneously as LOCK WAIT in MySQL's innodb_trx. It releases the lock, waits for both workers, and checks database state and aggregate mail/artifact counts. Workers use no real gateway, cloud or mail delivery. The harness is separate from the default suite and its three scenarios must not be added to the PHPUnit test total as three ordinary cases.

| Concurrent scenario | Required / observed |
| --- | --- |
| Two paid callbacks against an unconverted quotation | One invoice and item; one actual Common conversion; one callback notification and artifact |
| Paid plus pending against completed invoice | Completed state preserved; no additional notification/artifact |
| Cancelled plus paid against completed invoice | Completed state preserved; no additional notification/artifact |

All three scenarios pass in each of two harness runs, with two simultaneous SQL lock waits each. See [run 1](evidence/phase-2.3/concurrent-run-1.json) and [run 2](evidence/phase-2.3/concurrent-run-2.json). Scheduling order after lock release is nondeterministic; preservation holds for either order. These are normal completed-process concurrency tests, **not crash-safe exactly-once delivery**. Common currently catches conversion failures; a crash/commit failure after external delivery can leave incomplete or repeated effects. Durable idempotency/outbox/compensation requires separately accepted design and schema authorization.

For Product import, Mongo exceptions still propagate to the caller and SQL survives. A caller retry using valid provider input unconditionally upserts identity and attributes for the existing SQL product, repairing an absent or incomplete Mongo document. There is no automatic retry queue/background detector and no claim of atomicity. Concurrent first imports and pre-existing duplicate IDs still need uniqueness/ownership policy; no schema changes are authorized here.
