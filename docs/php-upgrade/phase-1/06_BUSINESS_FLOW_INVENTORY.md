## High-priority observations

- **VERIFIED source**: `Common.php` creates a Razorpay link before some PDF/email generation paths; a PDF test can therefore make a payment API call if it invokes the business flow. Mock the gateway at a boundary before testing full quotation creation.
- **VERIFIED source**: current CP template has a fixed company/address and generated optional tax rows; these are existing committed user changes, not audit changes. Preserve screenshots and obtain explicit output acceptance before changing template generation.
- **VERIFIED source**: `finalizePaidQuotationOrInvoice` checks conversion state, but static inspection is not a proof of idempotence. Do not label replay/concurrency behavior as passing without sandbox tests.
- **VERIFIED source**: several GET endpoints change status or invoke cron-like work. Do not crawl or smoke-test every route by issuing requests. Route enumeration is distinct from handler execution.
- **PENDING**: payment sandbox accounts, sample signed payloads, protected fixtures, baseline PDF/email screenshots, response snapshots, business-approved currency/tax cases and independent data stores. Existing PDFs/data in the checkout may contain real customer information and were not exported as fixtures.

Phase 2 should start by characterizing quotation → payment → invoice → PDF/email behavior, authentication and data access on the unchanged baseline, after Phase 1 recovery/isolation gates pass. Do not begin those tests against production or alter business behavior to make a new test pass during Phase 1.
